## 1. #009 無知のベールで発生した主要な躓き

今回もっとも大きかった問題は、**Canva上ではテキスト要素が存在しているのに、実際の表示では文字が見えなくなったこと**である。

原因は文字色・フォントサイズではなく、**全画面背景が文字より前面に置かれたレイヤー順**だった。

### 発生した誤対応

- 文字が見えない状態に対し、`#F2F3F5` / `#FFB000` の色を再適用した
- 太字を再適用した
- フォントサイズ・位置を調整した

これらはテキスト要素自体には作用するが、**背景が文字の前面にある場合は根本解決にならない**。

### 最終的に有効だった対応

```text
検証済み Layered テンプレートを複製
↓
各ページにもともと存在する全画面背景プレースホルダーを確認
↓
背景画像は insert_fill せず update_fill のみで差し替え
↓
既存の編集可能テキスト要素を新作品の内容へ置換
↓
文字色・サイズをBrand Shellへ統一
↓
全8ページの実サムネイルを確認
↓
ユーザー承認
↓
commit
```

この方式では、**背景レイヤーの上に文字レイヤーが存在する構造をテンプレートから引き継げる**。

## 2. レイヤー順を最優先で疑う条件

次の症状が出た場合、色やサイズを調整する前にレイヤー事故を疑う。

```text
- Canva API上ではtext elementが存在する
- テキスト内容も正しい
- 色も #F2F3F5 など十分に明るい
- 位置も画面内
- それでも実サムネイルで文字が見えない
```

この場合、第一仮説は：

> 全画面背景画像がテキストより前面にある

とする。

### 禁止する応急処置

レイヤー順が原因と疑われる状態で、以下を何度も繰り返さない。

- 色変更
- 太字化
- 文字サイズ拡大
- テキスト位置の微調整

それらは**レイヤー順を変えない**。

## 3. 全画面背景の絶対ルール

### 正しい方法

```text
既存の全画面背景プレースホルダー
→ update_fill
```

### 原則禁止

```text
insert_fill で1080×1920の背景画像を後から追加
```

全画面背景を後からinsertすると、背景が文字より前面に配置される可能性がある。

Canva編集APIで明示的な「最背面へ移動」が使えない場合、**後から追加した背景を安全に文字の背面へ戻せない**。

そのため、レイヤー事故が起きたデザインを無理に直すより、検証済みLayeredテンプレートから再構築する。

---

## 4. Canva Working Copyは1本に固定する

#009では修正過程で複数コピーが発生し、どのDesign IDが正本か分かりにくくなった。

今後は新作制作開始時に、次を1件だけ決める。

```text
CANONICAL WORKING DESIGN
Design ID: ...
Title: WORKING_{ID}_{作品名}
```

以降の編集・プレビュー・commitはこのDesign IDだけに対して行う。

### 再構築が必要になった場合

新しいLayeredコピーを作った瞬間に、旧Working Copyを正本から外す。

```text
OLD / ABANDONED
↓
NEW CANONICAL WORKING DESIGN
```

同時に複数のコピーを「完成候補」として扱わない。

### 保存時の確認

commitする直前に必ず確認する。

```text
[ ] 今見ているプレビューのDesign IDとcommit対象が同じ
[ ] ユーザーが承認したデザインと同じ
[ ] 旧コピーをcommitしようとしていない
```

## 5. 背景内の不要物とCanva要素を区別する

#009では、背景に人物状の形や余分な線が見える場面があった。

削除前に、その対象が：

1. 独立したCanva要素なのか
2. 背景画像に焼き込まれた一部なのか

を確認する。

### 独立要素の場合

`delete_element` で削除可能。

### 背景画像に焼き込まれている場合

Canva上でその部分だけを削除しようとしない。

```text
背景を再生成
または
別の背景assetへ update_fill
```

で修正する。

**「見えている＝独立Canva要素」とは限らない。**

## 6. v1.7追加QC：Layer Visibility QC

通常のBrand / Text / Background QCとは別に、全ページで実施する。

```text
[ ] 実サムネイルでブランド名が見える
[ ] 実サムネイルでページ番号が見える
[ ] kickerが見える
[ ] 主本文が見える
[ ] CTA / A/Bがあるページではそれらが見える
[ ] 背景が文字を覆っていない
[ ] text elementの存在確認だけで合格にしていない
```

### 重要

**APIのrichtext一覧に文字があることと、ユーザーが画面上で文字を読めることは別状態である。**

最終判断は実サムネイルを優先する。

```text
11. Brand / color / 改行QC
12. ユーザーへプレビュー
13. 明示承認後commit
14. commit後read-back
15. final folder audit
```

## 8. 「文字が見えない」トラブルシュート

| 症状 | 最初に疑う原因 | やってはいけないこと | 正しい対処 |
|---|---|---|---|
| text elementはあるが文字が見えない | 背景が文字より前面 | 色・サイズ調整を繰り返す | Layeredテンプレートから再構築しupdate_fill |
| 一部ページだけ文字が見えない | そのページだけinsert_fill等で構造が違う | 他ページと同じ見た目だけに合わせる | page単位でfill構造を確認 |
| 背景の人物・線を消したいが要素IDがない | 背景画像に焼き込み | 存在しないshapeを探し続ける | 背景assetを再生成・差し替え |
| 保存後に違う版が見える | 別コピーをcommit | さらに新コピーを増やす | Canonical Design IDを再確定 |
| プレビューでは良いが保存後に崩れる | commit対象違い / read-back不足 | 保存済みと即断 | commit後read-back |

## 10. #009 無知のベール｜確定知見

1. **全画面背景は既存fillを差し替える。後挿入しない。**
2. **文字が見えないとき、text elementが存在していても安心しない。**
3. **色・太字・サイズ変更はレイヤー事故の解決策ではない。**
4. **Layeredテンプレートの既存レイヤー順を利用するのが最も安定した。**
5. **複数コピーを作るとDesign ID取り違えが起きるため、正本を1件に固定する。**
6. **背景内の人物・線などが焼き込みなら、Canva要素削除ではなく背景差し替えで対応する。**
7. **全ページ実サムネイル確認後にcommitする。**
8. **ユーザーが画像完成を宣言するまでは、画像工程をCOMPLETE扱いしない。**

### #009で確立したレイヤー安全原則

```text
Layered template
→ existing background fill
→ update_fill
→ editable text above background
→ thumbnail QC
→ approval
→ commit
```

この順序を今後の標準とする。

## 11. #012 囚人のジレンマ｜背景と文字のコントラスト事故

#012ではレイヤー構造自体は正常だったが、**背景写真の局所的な明暗と文字色が衝突した**。

最初は暗い背景を前提に基本文字色 `#F2F3F5` を置いたが、写真内の照明・扉・壁など明るい領域に白文字が重なり、一部が読みにくくなった。

その後、該当補足文を一律に濃色へ変更したところ、今度は同じテキストボックス内または移動先の暗い領域で**黒系文字が背景へ沈む逆事故**が起きた。

### 今回の重要な反省

> **「背景全体が暗い／明るい」ではなく、文字ボックスが実際に重なる局所領域でコントラストを判定する。**

写真背景は1枚の中でも明暗差が大きい。したがって、ページ単位で「白文字」「黒文字」と決めるだけでは不十分である。

### 修正で有効だった優先順位

```text
1. 文字の位置を、背景の均一で暗いText Zoneへ移動できるか確認
2. 移動できるならBrand Shellの #F2F3F5 を維持
3. 位置変更だけでは解決しない場合のみ文字色変更を検討
4. 色変更後も実サムネイルで再確認
5. 白→黒にしただけで完了扱いしない
```

#012では、補足文・CTAを背景の明暗境界から外し、より均一な暗部へ移動して白文字へ戻す方が安定した。

## 12. Text Zoneは画像生成・選定時に確保する

従来のImage PlanでText Zoneを決めるだけでなく、**背景画像そのものの採用条件としてText Zoneのコントラスト安定性を確認する**。

背景候補を採用する前に次を確認する。

```text
[ ] 主本文予定領域に強い白飛び・照明・窓・光源がない
[ ] 補足文予定領域に極端な明暗境界がない
[ ] CTA予定領域が均一な暗部になっている
[ ] 人物・椅子・扉など重要被写体と文字が競合しない
[ ] Brand Shellの #F2F3F5 を基本のまま使える
```

### 背景選定の優先順位

```text
テーマ適合性
→ Text Zoneの確保
→ 被写体との非干渉
→ コントラスト安定性
→ 美しさ・雰囲気
```

見栄えが良くても、文字を安全に置けない画像は背景として不採用にする。

## 13. Contrast QCを独立工程に追加

Layer Visibility QCとは別に、**Contrast QC** を全ページで実施する。

### Layer Visibility QCが見るもの

- 背景が文字レイヤーを覆っていないか
- テキスト要素が実際に表示されているか

### Contrast QCが見るもの

- 表示されている文字が背景に対して十分読めるか
- 白文字が明部へ重なっていないか
- 黒系文字が暗部へ重なっていないか
- 文字列の途中で背景明度が大きく変化していないか

チェックリスト：

```text
[ ] ブランド名が読める
[ ] ページ番号が読める
[ ] kickerが読める
[ ] 主本文の全行が読める
[ ] 補足文の全行が読める
[ ] A/Bの両方が同程度に読める
[ ] CTAが読める
[ ] 文字ボックスの一部だけが白飛び／黒つぶれしていない
[ ] スマホ縮小表示でも一読できる
```

**「文字が存在する」ではなく、「全行が瞬時に読める」を合格条件とする。**

---

## 14. 文字色変更より位置変更を優先する

ブランドの一貫性を維持するため、背景との衝突時は原則として次の順で直す。

```text
位置変更
→ 必要ならサイズ・改行の微調整
→ それでも無理なら文字色変更
→ それでも不安定なら背景差し替え
```

基本文字色 `#F2F3F5` と標準アクセント `#FFB000` を可能な限り維持する。

黒・濃色文字は、背景の明部が十分広く、文字ボックス全体で明度が安定している場合にのみ例外的に使う。一部分だけ明るい背景を理由に、文章全体を黒へ変更しない。

### 禁止する修正

```text
NG: 白文字が一部見づらい → とりあえず全文黒
NG: 黒文字が沈む → とりあえず全文白
NG: 1枚のプレビューだけ見て全ページへ同じ色変更
```

## 15. Canva実装フローを更新

#012の知見を反映し、Canva工程を次へ更新する。

```text
1. 検証済みLayeredテンプレートを1回だけ複製
2. Canonical Working Design IDを確定
3. 既存full-page background fillを確認
4. 背景を update_fill
5. Final Copyを既存text elementへ置換
6. Brand Token Reset
7. Text Zone / size / line break調整
8. 全ページ実サムネイル取得
9. Layer Visibility QC
10. Contrast QC ← NEW
11. 旧テーマQC
12. Brand / color / 改行QC
13. コントラストNGは「位置→改行/サイズ→色→背景」の順で修正
14. 修正ページの実サムネイルを再取得
15. ユーザーへプレビュー
16. 明示承認後commit
17. commit後read-back
18. final folder audit
```

### 完成判定の追加条件

ユーザーへ「画像完成候補」と伝える前に、少なくとも次を満たす。

```text
[ ] 全ページの実サムネイルを直近の編集状態で確認した
[ ] Layer Visibility QC PASS
[ ] Contrast QC PASS
[ ] 白被り・黒被りがない
[ ] Brand Shellを不必要に崩していない
[ ] ユーザーが画像完成を承認した
```

## 16. #012で確立したコントラスト安全原則

1. **背景写真はページ全体ではなくText Zone単位で明暗を見る。**
2. **白被りを黒文字への一律変更で解決しない。逆事故が起こり得る。**
3. **Brand Shellを維持できるなら、色変更より位置変更を優先する。**
4. **Text Zoneを確保できない背景は、画像として美しくても採用しない。**
5. **Layer Visibility QCとContrast QCは別工程として両方行う。**
6. **修正後は変更ページの実サムネイルを必ず再取得する。**
7. **「白被りが消えた」だけでなく「黒被りもない」ことを同時に確認する。**
8. **ユーザーが画像完成を宣言するまでは画像工程をCOMPLETE扱いしない。**

### #012で確立したコントラスト安全フロー

```text
Background candidate
→ Text Zone contrast check
→ Brand Shell text
→ actual thumbnail
→ Layer Visibility QC
→ Contrast QC
→ position first
→ color only if necessary
→ thumbnail re-check
→ user approval
→ commit
```
